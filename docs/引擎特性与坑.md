# Godot 4.7.2 引擎特性与坑（实测记录）

本项目所有结论均在本机实测得出，环境：
Godot 4.7.2 stable（标准版，非 .NET）、Windows 10 22H2、RTX 5060 Ti、Vulkan 1.4.329、Forward+。

---

## 1. 中文字体加载

**结论：必须用 `FontFile.load_dynamic_font(<绝对路径>)`，不要依赖 `SystemFont` 的名字匹配。**

实测系统字体（`C:/Windows/Fonts/`）：

| 字体 | 文件 | 用途 |
|---|---|---|
| 仿宋 | `simfang.ttf` | **工程字主字体**，配合 0.7 横缩即国标长仿宋 |
| 黑体 | `simhei.ttf` | 标题字 |
| 楷体 | `simkai.ttf` | 说明文字 |
| 宋体 | `simsun.ttc` | 备用 |
| 微软雅黑 | `msyh.ttc` | 界面字体 |
| Noto Sans SC | `NotoSansSC-VF.ttf` | **OFL 开源**，可打包分发的兜底字体 |

`OS.get_system_font_path()` 对以下名字均能正确解析，可用来定位系统字体：
`FangSong` / `仿宋` / `SimSun` / `宋体` / `SimHei` / `黑体` / `KaiTi` / `Microsoft YaHei` / `Noto Sans SC`

### 长仿宋的实现
国标 GB/T 50001 规定汉字用长仿宋体、宽高比 0.7。无需寻找专门的长仿宋字体文件，
对普通仿宋施加横向 0.7 压缩即可，实测效果正确：

```gdscript
var ff := FontFile.new()
ff.load_dynamic_font("C:/Windows/Fonts/simfang.ttf")
var fv := FontVariation.new()
fv.base_font = ff
# 注意：Transform2D 是列向量构造，不是 6 个标量
fv.variation_transform = Transform2D(Vector2(0.7, 0.0), Vector2(0.0, 1.0), Vector2.ZERO)
```

字母数字的 75° 斜体（国标允许正体或 75° 斜体）同理，用剪切矩阵：
`Transform2D(Vector2(1.0, 0.0), Vector2(0.2679492, 1.0), Vector2.ZERO)`
（`tan(75°) ≈ 3.732`，剪切系数取 `1/tan(75°) ≈ 0.2679`）

### 字体授权
`simfang.ttf` 等随 Windows 分发，不可打包进软件再分发。
策略：**优先读系统已安装字体（本机渲染，合法）**，找不到时回退到内置的
开源仿宋（朱雀仿宋 / 汇文仿宋，均为 SIL OFL-1.1，可自由商用）。
**禁止把 `C:/Windows/Fonts/*` 下的字体复制进 `assets/` 一起分发。**

## 2. 截图验证必须预热字体图集

**这是本项目踩过的最大的一个坑，曾导致近乎错误的架构决策。**

现象：程序刚启动的头几帧抓图，所有文字（含拉丁字母）都渲染成**实心方块**，
且方块宽度等于字形步进宽度——说明字形几何正确、但采样到的是纯白占位纹理。
换成矢量线段则完全正常。

**根因：动态字体的字形图集是延迟光栅化的。** 首次 `draw_string` 触发 CPU 侧光栅化，
图集纹理要过若干帧才提交到 GPU。在此之前抓帧就会拍到白色占位纹理。

**已验证的结论（程序化像素比对，非肉眼判断）：**
- 在第 4 帧、第 31 帧、第 61 帧分别抓图，**两两差异均为 0.0000%** → 第 4 帧已完全正常且稳定。
- 在第 3 帧抓图 → 出现方块。
- **与 `msaa_2d` 无关。** 曾误判为 `msaa_2d=2` 破坏字体渲染，实测
  `msaa_2d=2`（4x MSAA）下文字与矢量线均完全正确。

**规避方法：截图工具必须先预热再抓帧。**

```gdscript
# 1) 强制光栅化：对将要用到的文字调用一次度量接口
font.get_string_size("长仿宋工程字", HORIZONTAL_ALIGNMENT_LEFT, -1, 32)
# 2) 等待足够帧数（实测 4 帧已够，工程上留 8~10 帧余量）后再抓
for i in range(10):
    await RenderingServer.frame_post_draw
var img := get_viewport().get_texture().get_image()
```

**教训：不要凭单次截图肉眼判断渲染缺陷，先确认是不是抓帧时机问题。**
程序化比对（多帧像素 diff）比看图可靠得多。

## 3. 抗锯齿方案

`msaa_2d` 可正常使用，且对矢量线的抗锯齿效果良好。

| 方案 | 线条质量 | 代价 |
|---|---|---|
| `msaa_2d = 4x` + `draw_multiline` | 好 | 视口级 MSAA 缓冲，无额外顶点 |
| `msaa_2d = 0` + `draw_polyline(antialiased=true)` | 接近 MSAA，细线略偏淡 | 每条曲线一次提交，顶点数约 3 倍 |
| `msaa_2d = 0` + `draw_multiline` | 明显锯齿 | 最快 |

**定案：用 `msaa_2d = 4x`，几何走 `draw_multiline` 批量提交。**
`draw_multiline` 没有 `antialiased` 参数，但在 MSAA 下由 MSAA 提供抗锯齿，
是质量与性能的最优组合。

注意 `draw_arc` 的分段数固定，放大后会露出多边形棱角。
圆弧必须按**屏幕像素矢高**自适应细分（本项目取 0.25px 矢高），不能用固定分段数。

## 4. 无头模式与脚本运行

- `godot --headless --script res://x.gd` **要求脚本继承 `SceneTree` 或 `MainLoop`**，
  普通 `extends Node` 的脚本会报 "doesn't inherit from SceneTree or MainLoop"。
- 要在无头模式下跑普通场景脚本，改用**场景作为位置参数**：
  `godot --path <项目> res://tests/xxx.tscn`
- **`--headless` 下没有渲染设备，抓帧会失败。** 截图必须在有窗口的模式下跑。
- 首次打开项目必须先生成全局类缓存，否则 `class_name` 全局类不可见：
  `godot --headless --path <项目> --import`
- `--resolution` 会被 `window/size/mode=2`（最大化）覆盖，
  要固定截图尺寸需在脚本里 `DisplayServer.window_set_mode(WINDOW_MODE_WINDOWED)`
  + `window_set_size()`。
- 脚本报错后**不会自动退出**，会挂住窗口。批量任务务必加 `--quit-after <帧数>` 兜底。
- 用 `| tail -n` 管道会缓冲到进程结束，调试时看不到进度；应直接重定向到文件。

## 5. 其他 API 细节

- `Transform2D` **没有 6 个标量的构造函数**，必须用列向量形式：
  `Transform2D(Vector2, Vector2, Vector2)`。误用会报
  "No constructor of Transform2D matches the signature"。
- `FontFile.get_cache_ascent(cache_index, size)` 需要 **2 个参数**（不是 1 个）。
- `FontFile.get_texture_image(cache_index, size, texture_index)`；
  纹理数量用 `get_texture_count(cache_index, size)`。
- **Vulkan 下 `FontFile.get_texture_image()` 返回的图集副本不可靠**（实测为纯白），
  不能用它来判断字形光栅化是否正确。判断字形是否正常只能通过实际渲染 + 抓帧。

## 6. 分桶几何必须是模型坐标（一次二次变换的教训）

**现象**：用户报告"客厅处的黄线会跟随缩放改变位置"。尺寸数字留在原处不动，
只有尺寸线在跑 —— 因为数字走文字通道（正确），线走了分桶通道（错误）。

**根因**：渲染器的分桶契约是"桶里只放模型坐标，屏幕变换在提交时用一次
`Transform2D` 乘法统一完成"。但连续线型图元走了一条名为
`emit_screen_segments(xf, ...)` 的快捷路径 —— 它是性能重构前的遗留物，
在入桶前就把坐标变换到了屏幕空间，提交时 `_flush` 又变换一次。
于是这些图元被**变换两次**，位置随缩放漂移。

**为什么只有黄色层看得见这个问题**：其它层恰好走了别的分支 ——
轴线是 CENTER 线型（走模型空间分支）、墙体走并集轮廓、门窗/楼梯是块引用、
填充走辅助通道。只有"连续线型的普通图元"命中那条路径，
示例图里正好只有尺寸标注层是这种组合。

**修复**：`emit_screen_segments` 改名 `emit_segments` 并**去掉 Transform2D 参数**。
不是"记得别用"，而是**根本拿不到**视图变换，从签名上杜绝重犯。
`_emit_curve` / `_emit_insert` / `_emit_walls` 同样删掉了用不到的视图变换参数。

**教训（值得单独记）**：
- 用像素比对**发现不了**这类缺陷。二次变换的误差是自洽的：
  低倍图上那个错误位置换算成模型坐标，正好就是高倍图上要画的位置，
  两张图点对点比对反而吻合（实测只差 0.24%，会被当成抗锯齿噪声放过去）。
- 决定性证据是**直接倾倒渲染器的分桶**：其它桶的范围都是几千毫米量级，
  只有黄色桶是 `(-165,-90)-(1214,790)` —— 一眼就看出是屏幕坐标。
  **怀疑渲染时，先看渲染器的中间数据，不要先看图。**
- 加了两个方向的回归断言（`tests/test_render.gd` 的分桶不变性 +
  `tests/capture.gd` 的"尺寸线落位/黄色越界"像素检查），
  并且都用"把缺陷改回去"验证过它们真的会失败。

**顺带记下的两个坑**：
- 黄色判据若写成"偏红"（`r > b * 1.6`），**X 轴的红线**会被整条误判成黄色，
  造成 15% 的假越界。必须同时要求 `g > r * 0.55`。
- 验证"某像素是否落在某层几何附近"时，标格子必须**沿线段按步长补点**，
  只标曲线顶点会让长直线的中段把自己线上的像素判成越界。

# 性能实测与瓶颈分析

基准工具：`tests/bench.tscn`（需有窗口运行，无头模式没有渲染设备）。
环境：Godot 4.7.2 / Windows 10 / RTX 5060 Ti / i5-11400。
所有计时为实测中位数，图元为随机散布的直线，跨度 120m（相当于几栋楼的体量）。

---

## 当前实测数据

| 图元数 | 四叉树重建 | 单次拾取 | 单次框选 | 渲染一帧（全可见） |
|---|---|---|---|---|
| 10 000 | 78 ms | 0.19 ms | 0.61 ms | **26.6 ms** |
| 50 000 | 385 ms | 1.47 ms | 3.77 ms | **137.9 ms** |
| 100 000 | 756 ms | 3.33 ms | 7.48 ms | **274.0 ms** |

图案填充（计算最重的图元）：50 个 6×6m 钢筋混凝土填充，共 23550 条线段，
**首次生成 120 ms，缓存命中 0.7 ms**。
缓存按「边界 + 图案参数 + 出图比例」的指纹失效。

文字密集场景：2000 条文字渲染一帧 **18.0 ms**。

### 判读

- **拾取与框选完全达标**：十万图元下单次拾取 3.3ms、框选 7.5ms，
  都远在一帧预算（16.7ms）之内。四叉树的设计是对的。
- **渲染是瓶颈**：十万图元全可见时 274ms，远超 16.7ms 的预算。
- **填充缓存有效**：首次生成慢（图案要逐条铺排并裁剪到边界内），
  但按指纹缓存后降到 0.7ms，编辑时才会重算。这个取舍是对的。

注意这是**最坏情况**：把缩放调到刚好容纳全部图元，一个都不剔除。
实际出图时视口只显示图幅范围的一部分，剔除会显著降低工作量。

---

## 已做的优化（累计约 3.8 倍）

1. **曲线缓存**：`CadEntity.get_curves()` 的结果缓存，随几何变更失效。
   此前每帧为每个图元重新解析几何，块引用与墙体轮廓尤其昂贵。
2. **零分配输出路径**：`emit_screen_segments()` 直接把屏幕空间线段追加到桶里。
   此前要经过「tessellate 生成模型点串 → Transform2D 乘出新数组」，
   每帧每图元两三次数组分配。直线覆写后完全消除分配。
3. **图层解析缓存**：图层名 → {可见性, 颜色, 线宽, 线型, 桶} 每帧建一次。
   此前每个图元要做四五次字典查找（可见性/颜色/线宽/线型），
   十万图元下这些查找本身就是主要开销。

## 尚未解决：架构性的剩余瓶颈

剩余成本的本质是：**每帧在 GDScript 里把十万个点变换到屏幕空间**。
每个点的变换、追加、以及 GDScript 的函数调用开销，是无法靠常数优化消除的。

彻底的解法是改变渲染模型：

> **以模型空间绘制几何，用 CanvasItem 的 transform 承载视图变换。**
> 这样点的变换由引擎的 C++ 在 GPU 侧完成，平移完全不花 CPU 时间。
> 代价是线宽会随缩放变化，需要把缩放量化到档位
> （例如每变化 10% 才重建一次），并接受缩放时的一次重建。

配套还要把视口裁剪从屏幕空间改到模型空间。

这是下一步该做的事，但它会改动渲染器、绘图视口、填充与实心路径，
属于结构性重构，需要在有充分预算时一次做完，不能半途而废。

## 另一个可做的小优化

鼠标移动时当前会触发整块几何重绘（因为十字光标和几何在同一个 CanvasItem 上）。
把十字光标与捕捉标记挪到**独立的 CanvasItem** 后，
鼠标移动只会重绘光标层，几何层的绘制命令由引擎缓存复用。
这在「只想移动鼠标看看」的场景下能省掉全部几何重绘开销。
